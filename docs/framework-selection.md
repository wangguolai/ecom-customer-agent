# 框架选型：为什么手写 ReAct，不用 LangChain / LangGraph / CrewAI / AutoGen

> 对应 README 第 6 项「说明『为什么用这个框架不用那个』」。
> 这是 architecture.md 选型表「手写 ReAct，不套 LangGraph/LangChain」那一格的展开——补全「那个」到底是什么。
> 来源：2026-08-20 WebSearch 调研。

---

## 一句话结论

**这个项目手写 ReAct，不是因为「手写更好」，而是因为项目目标是「理解底层 + 说明」，手写才能踩到坑、说明「LLM 只输出指令、代码才执行」。换成生产产品，大概率该用 LangGraph。**

---

## 四个框架分别是什么

| 框架 | 是什么 | 适合 | 短板 |
|------|--------|------|------|
| **LangChain** | 高层「全家桶」：LLM 封装、Prompt 模板、工具调用、向量存储、记忆 | 生态最广、组件多、上手快 | 线性执行、不支持循环/分支；`AgentExecutor` 已废弃要迁 LangGraph；抽象层多、调试难 |
| **LangGraph** | 底层图编排引擎：状态机 + 有向图（节点/边/全局状态），可脱离 LangChain 单独用 | 确定性控制最强、支持循环/分支/断点/Human-in-the-loop、生产就绪度最高 | 学习曲线陡、代码量大，简单场景偏重 |
| **CrewAI** | 角色化多 agent 团队（Agent/Task/Crew） | 上手最快、代码最少、贴近真实团队协作、快速原型 | 复杂分支控制弱、调试难（"deceptively simple"）、简单任务 token 消耗比 LangGraph 高约 3 倍 |
| **AutoGen** | 对话驱动多 agent（消息传递），微软出品 | 代码生成、沙箱执行、多视角辩论 | **2026 年已进维护模式**，微软把新用户导向 MAF（Agent Framework）；流程不可控、token 易失控 |

---

## 为什么这个项目不用它们（可直接照答）

**不用 LangChain**：它的 Agent 模式把整个 ReAct 循环藏进一次 `invoke()` 调用里，是个黑盒——你看不到「LLM 这一步为什么决定调这个工具」。本项目要说明「LLM 只输出 JSON 指令、代码才执行」，框架把这个要点盖住了。而且 `AgentExecutor` 已废弃、API 碎片化，学它还带一堆历史包袱。

**不用 LangGraph**：LangGraph 的价值在「多步骤编排 + 循环/分支/审批」的复杂场景，用图把状态流转显式化。但本项目是「单 agent + 工具调用」的简单结构，没有复杂的图拓扑，上 LangGraph 是杀鸡用牛刀——为了一个线性循环去搭状态机，代码量反而翻倍。

**不用 CrewAI**：CrewAI 是多 agent 框架，核心卖点是「角色化团队协作」。本项目的定位就是「单 agent ReAct + RAG」，**多 agent 不是需求**（10 步以内的任务，带好工具的单 agent 反而优于多 agent——多 agent 有协调开销、上下文重复、故障模式）。为了「多 agent」而上 CrewAI，等于先造一个不需要的复杂度。

**不用 AutoGen**：它 2026 年已经进维护模式，微软把新用户导向 MAF，新项目不该选它；而且它也是对话驱动多 agent，和 CrewAI 同理不适合本项目。

---

## 手写的代价（诚实讲，这反而是加分项）

手写 ReAct 的难点不在循环，在**防御**：max_steps 防死循环、连续相同调用判卡死、幻觉工具校验、token 截断、写操作权限开关——这些框架都替你做了。手写要自己实现，容易漏（静默死循环是最常见的坑）。

**但「手写这些防御」恰恰是这个项目的核心价值**：考的是「五类生产坑的现象→定位→解决」，用框架根本踩不到这些坑。所以本项目「手写 + 踩坑」是**刻意的技术选型，不是技术选型的结论**。

## 什么时候该换框架（加分句）

> 「当手写 Agent 开始出现工具协议、状态分支、恢复、审计、长期记忆这些需求时，就该把这些边界迁移到框架抽象里——核心逻辑手写、边缘功能用框架，是常见折中。」

这句话能证明你不是「无脑手写党」，而是「知道手写的边界在哪」。

## 模拟：为什么不用 CrewAI？

> 问：你项目为什么手写 ReAct，不用 CrewAI？
> 答：三个原因。第一，CrewAI 是多 agent 框架，核心是角色化团队协作，而我这个客服项目是「单 agent + 工具调用」，10 步以内的任务带好工具的单 agent 反而优于多 agent，多 agent 的协调开销、上下文重复、故障模式我都不需要。第二，我的项目目标是搞清「LLM 只输出指令、代码才执行」的底层，框架会把循环藏起来，踩不到五类坑。第三，CrewAI 简单任务 token 消耗比 LangGraph 高约 3 倍，对一个客服场景不划算。如果哪天要做「多 agent 协作」或者「需要断点续跑/审计」的复杂编排，我会优先考虑 LangGraph 而不是 CrewAI，因为它的确定性控制和生产就绪度更高。
