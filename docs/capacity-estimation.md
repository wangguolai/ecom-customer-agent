# 容量估算（Back-of-the-Envelope Estimation）

> 系统设计主线的**量化半场**。配套 `-mine.md` Q9「10 万并发」——Q9 铺「怎么扩」的架构，这里补「扩多少」的数字。
> 2026-09-03 补讲。系统设计题「10 万并发怎么设计」：定性（加缓存/分库分表/上集群）之外必须能量化（几台/几个库/多大缓存），否则是吹水。

## 为什么

- 架构设计分两半：**定性**（qualitative，怎么拆）+ **量化**（quantitative，拆多少）。
- 系统设计要验证的是量化能力：「到底几台机器？分几个库？缓存多大内存？」
- 来源：Google/微软系统设计的 Back-of-the-envelope estimation（信封背面估算，即「拿张纸粗略算量级」）。

## 一、五个词，别混（术语中英对照 + 歧义点破）

| 词 | 英文 | 含义 | 单位 |
|----|------|------|------|
| 并发连接数 | concurrency | 同时在线/活跃的连接数 | 个 |
| QPS | Queries Per Second | 每秒查询/请求数 | 次/秒 |
| TPS | Transactions Per Second | 每秒事务数 | 笔/秒 |
| 吞吐量 | throughput | 每秒处理的数据量 | MB/s |
| 延迟 | latency | 单个请求的响应时间 | ms |

**最大的歧义坑**：「10 万并发」的「并发」= 并发连接数，**不是 QPS**。两者差一个「每用户每秒发几个请求」的系数——在线用户大部分时间在「看」不在「请求」。

## 二、第一步：并发 → QPS 换算（最大要点）

```
QPS = 并发连接数 × 每连接每秒请求数
```

每连接每秒请求数（经验值）：客服/电商场景 0.1~0.2（每 5~10 秒一个请求）。

```
10 万并发在线 × 0.1 = 1 万 QPS   ← 差 10 倍
```

拿「10 万」直接当 QPS 算，机器数虚高 10 倍。第一句就是反问「10 万是并发还是 QPS」。

**另一种换算法（从日活 DAU 推）**：

```
QPS = DAU × 人均日请求数 / 86400 × 峰值系数
```

- 峰值系数（peak factor）2~10：流量不均匀，80% 流量集中在 20% 时间（8/2 原则）。
- 秒杀类脉冲场景系数会爆，不适用线性估。

## 三、第二步：量级表（信封背面的全部弹药）

| 组件 | 单机量级 | 为什么 |
|------|---------|--------|
| 无状态应用服务器 | 1000~5000 QPS | 带 DB 查询慢、纯计算快 |
| MySQL | 单机几千 QPS | 磁盘+索引，单行快、join 慢 |
| Redis | 单机 10 万 QPS | 纯内存 |
| Kafka | 单机几十万条/秒 | 顺序写磁盘 |
| Nginx | 几万~几十万 QPS | 静态/转发，无业务逻辑 |

**直觉就一句：内存 > 磁盘，简单逻辑 > DB 依赖 → 瓶颈几乎永远在 DB。** 呼应「分库分表最贵」——应用层/缓存加机器就扩，DB 扩要分库分表 + 数据迁移。

## 四、第三步：完整例子（10 万并发在线客服）

| 层 | 估算 | 结论 |
|----|------|------|
| QPS | 10万 × 0.1 | 1 万 QPS |
| 应用服务器 | 1万/1000 = 10台，×1.5 冗余 | 15 台 |
| DB | 缓存命中 90% → 只扛 1000 QPS | 单机够，加主从读写分离 |
| Redis | 1万 << 10万 | 单机够；内存 100万 × 1KB = 1GB |
| 存储 | 日 100万 × 1KB = 1GB/天 | 留 3 年 ≈ 1TB |
| 带宽 | 1万 × 10KB = 100MB/s = 800Mbps | Gbps 级 |
| MQ | 写占 10% = 1000条/秒 | 单机够，算积压深度 |

## 五、设计要点

1. **先澄清并发 vs QPS**——最大坑，第一个要点。
2. **量级对就行**——看 10 台还是 100 台，不看到个位。
3. **每步给依据**——「单机 1000 因带 DB 查询」「90% 因热点集中」，依据比数字值钱。
4. **留冗余**——30%~50% + 单点容错。
5. **结论落 DB 瓶颈**——呼应分库分表最贵，前后串成一条线。

## 六、反例（禁止行为）

- ❌ 拿并发当 QPS → 机器数虚高 10 倍。
- ❌ 延迟和吞吐混着说 → 一个请求多快 vs 一秒处理多少，优化方向不同。
- ❌ 不看缓存命中率，假设全打 DB → DB 压力算满，机器数虚高。
- ❌ 按平均不按峰值 → 高峰被冲垮。

## 七、估算不准怎么办（容量管理是闭环，不是一次算对）

被问「你估的准吗？」「上线发现估少了/估多了怎么办？」——标准答法：

- **估不准是常态**——业务系数（每用户每秒请求数）、峰值系数都是经验值，不可能准。
- **不靠「一次估准」，靠「估算给初始值 + 监控驱动扩容 + 限流降级兜底」的闭环**：
  1. 上线按「估算初始值 + 30%~50% 冗余」部署，不按理论峰值堆满（避免烧钱）。
  2. 上线后监控真实指标（QPS / CPU / 内存 / 延迟 / 错误率）。
  3. 触发阈值 → 扩容（K8s HPA 弹性伸缩 / 手动加机器）；负载低 → 缩容省成本。
  4. 估少了 → 限流兜住（超了拒，保护服务，牺牲部分体验）+ 降级（核心保住、非核心牺牲），不会被打崩。
- **限流/熔断/降级的另一重身份**：不只是「防攻击/防下游挂」，本质是「容量估错的保险」——估不准没关系，有兜底。

**和项目串联**：高可用模块（限流/熔断/降级）已在代码落地，正是容量闭环的兜底一环。可以说明「我的限流不是孤立防刷，是容量管理闭环的兜底——估算给初始值，限流兜住估错，监控驱动扩容」。
