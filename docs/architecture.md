# 电商客服 Agent 架构图

> 系统设计主线。分层架构 + 数据流 + 选型理由。用。

## 1. 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│                      用户问题（自然语言）                      │
└───────────────────────────┬─────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│              AgentSession（多轮会话）                          │
│   维护历史 messages + 摘要压缩（超预算压旧轮为摘要）            │
└───────────────────────────┬─────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│              ReAct 循环（手写，不套框架）                       │
│   LLM 决策 → 工具调度 → 结果回灌 → 再决策（max 8 步）           │
│   防御：幻觉校验 / 死循环检测 / 参数校验 / Token 截断            │
└───────────────────────────┬─────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                   工具层（6 个工具，Function Calling）           │
│  search_products │ search_orders │ search_logistics           │
│  check_stock     │ get_return_policy │ transfer_to_human      │
└───────┬──────────────────────────────┬───────────────────────┘
        │（商品咨询）                    │（订单/物流/库存/转人工）
        ↓                              ↓
┌───────────────────┐          ┌───────────────────┐
│   RAG 检索（混合）  │          │    mock 数据       │
│ 预过滤(类别) → BM25+向量 │    │  订单/物流/库存     │
│  → 双低拒答 → RRF 融合  │    │  （内存硬编码）      │
│  → Rerank 精排     │          │                   │
└─────────┬─────────┘          └───────────────────┘
          ↓
┌─────────────────────────────────────────────────────────────┐
│                      基础设施层                                │
│   DeepSeek（LLM） │ BGE-small-zh（embedding） │ Qdrant（向量库）│
│                 BGE-Reranker-v2-m3（精排）                    │
└─────────────────────────────────────────────────────────────┘
```

## 2. 数据流（一句话）

用户问题 → AgentSession 追加历史 → ReAct 循环让 LLM 输出 `tool_calls`（JSON 指令）→ 代码执行对应工具（商品咨询走 RAG，订单物流走 FastAPI 后端）→ 结果回灌 → LLM 再决策 → 最终答案。

## 3. 选型理由（必问「为什么这么选」）

> 全量选型对比（每个选择的替代方案 + 为什么不用）见 [tech-selection.md](tech-selection.md)。

| 决策点 | 选择 | 为什么 |
|--------|------|--------|
| LLM | DeepSeek（deepseek-chat） | 便宜 + 中文好 + OpenAI 兼容（原生支持 Function Calling） |
| Agent 编排 | **手写 ReAct 循环**，不套 LangGraph/LangChain | 理解底层「LLM 只输出指令、代码才执行」，要说明循环；框架封装了循环反而盖住要点 |
| 工具交互 | Function Calling（不手写正则 ReAct） | API 契约保证格式可靠，避免「正则解析 Thought:/Action:」的格式地狱 |
| RAG 角色 | 包装成 `search_products` 工具，和其他工具平级 | RAG 在 agent 里就是一个查询工具，路由交给 ReAct 自动选，不用写 if-else |
| Embedding | BGE-small-zh-v1.5（512 维） | 中文优化 + 本地免费（零 API 成本）+ 数据量小 512 维够用 |
| 向量库 | Qdrant 本地文件模式 | 无需 Docker（中国大陆网络限制）+ API 简洁 + 数据量小本地够用 |
| 检索策略 | category 预过滤（召回阶段）→ BM25+向量混合召回 → 双低拒答 → RRF 融合 → Rerank 精排 | 预过滤在召回时就锁类别（向量+BM25 都只在类别内搜），Rerank 只对已锁类别的候选精排、不为错误答案浪费推理；「召回优先 or 拒答」的策略动机见 3.2 |
| 动态数据 | 价格/库存走工具实时查，不写进向量库 | 数据分治：向量库是「快照」，动态数据走工具才有时效性 |
| 多轮记忆 | 全量保留 + 摘要压缩（超预算压旧轮为摘要，保留关键实体） | 丢轮次会丢订单号（断跨轮指代），摘要压缩用可控 token 代价换关键信息不丢 |
| 防御 | 白名单 + 步数上限 + 截断 + 数据/指令分离 | 五类坑的「层层兜底」，不追求「一次保证 LLM 走对」 |

### 3.1 量化数据（「有一个量化数据」硬项）

| 指标 | 数值 | 说明 |
|------|------|------|
| 混合检索 Recall@3 | 0.57 → **0.97** | 推翻 Rerank 绝对阈值（0.6 误杀口语 query）→ 改召回层双低拒答；30 条四档难度评测集 |
| Rerank 延迟 | 170ms → **16ms** | torch CPU 版 → CUDA（RTX 5070） |
| 评测指标 | Recall@3 + MRR 双指标 | `tests/eval_retrieval.py`，按难度梯度四档标注（字面基线 → 场景描述） |

### 3.2 召回策略：为什么「召回优先、拒答兜底」（场景驱动，必讲）

这是**电商客服场景**的策略，不是通用结论：

- **动机是转化率**：卖东西看转化率，宁可多召回、不轻易拒答。把「判断权 + 话术权」交给 LLM 做客服回复润色，而不是在召回层用绝对阈值误杀边界 query——昨天踩的坑就是 Rerank 绝对阈值 0.6 误杀口语 query（Recall 0.97 掉到 0.57），改成召回层双低拒答才回到 0.97。
- **四维置信度分类 → 对应策略**（昨天定的细化方向，代码待落地）：

  | 召回层状态 | 判断标准 | 策略 |
  |-----------|---------|------|
  | 双高 | 向量 + BM25 都命中同一答案 | 直接推 |
  | 单高一致 | 两路 top1 相同 | 软推 + 确认 |
  | 单高冲突 | 两路 top1 不同（如「出门乱跑」向量=漏食球错、BM25=牵引绳对） | 列候选让用户选 / 优先信精确词（BM25）那一路 |
  | 双低 | 向量 top1 低分 + BM25 无召回 | 拒答 / 转人工 |

- **三层结构（判断与生成分离）**：①置信度判断层（硬编码规则）→ ②策略映射层（硬编码规则）→ ③话术生成层（LLM 按「策略标签 + 检索结果」生成话术）。前两层确定性、可测试，只有话术交给 LLM——和「验证与生成分离」同一哲学。四维分类 + 三层已落地（`_classify` + `STRATEGY_HINTS`）。

- **场景相关性（关键）**：这套「召回优先」是电商的答案，不是普适的。换成**医院问药品**——安全优先、错不得，策略要反过来：宁可拒答转人工，也不给低置信度答案。**策略跟着业务目标走，不是跟着检索指标走。**

## 4. 当前状态与不足（「诚实讲不足」用）

- 订单/物流/库存已接 FastAPI + SQLite 后端（真实 HTTP 接口 + 超时降级），但后端数据是**种子数据**（非生产数据），转人工仍是 mock
- Prompt Injection 已做 prompt 级（数据/指令分离）+ 代码级（写操作权限开关：refund 待审批 + 参数校验 + 读/写分离），但「待审批」是 mock（无真实审批流程）
- 评测做了检索层（Recall@3 + MRR）+ 脏输入四档测试，Agent 级评测（LLM-as-judge）只做了最小版验证、未正式落地
- 可观测已做（Trace + MetricsStore：技术成功率 / P99 / 平均延迟 / 平均 token），可视化层生产接 LangSmith
