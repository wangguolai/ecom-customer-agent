# 电商客服 Agent 架构图

> 系统设计主线。用。主链路（分层）+ 后端横切线 + 三条横切线（数据层 / 评测 / 可观测）+ 选型理由。

## 1. 主链路架构（分层）

```
┌─────────────────────────────────────────────────────────────┐
│                      用户问题（自然语言）                      │
└───────────────────────────┬─────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│              AgentSession（多轮会话）                          │
│   维护历史 messages + 摘要压缩（超预算压旧轮为摘要）            │
└───────────────────────────┬─────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│              意图路由（规则优先，LLM 兜底）                     │
│  规则命中（订单/物流/政策/转人工/浏览/总结）→ 直接执行工具       │
│  未命中 → ReAct 循环（手写：LLM 决策 → 工具 → 回灌，max 8 步）  │
│  防御：幻觉校验 / 死循环检测 / 参数校验 / Token 截断            │
└───────────────────────────┬─────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                工具层（8 个工具，Function Calling）              │
│  search_products │ search_orders │ search_logistics           │
│  check_stock     │ get_return_policy │ check_online            │
│  refund_order（写）│ transfer_to_human（写）                    │
└───────┬──────────────────────────────┬───────────────────────┘
        │（商品咨询）                    │（订单/物流/库存/退款/转人工）
        ↓                              ↓
┌───────────────────┐          ┌───────────────────────────────┐
│   RAG 检索（混合）  │          │     FastAPI 后端（真实数据源）    │
│ 预过滤(类别) →      │          │  /orders /logistics /products   │
│  BM25+向量 →        │          │  /online /refund /auth/token    │
│  双低拒答 → RRF 融合 │          │  review /execute（挂 JWT）      │
│  → Rerank 精排     │          │  【后端横切线见 1.1】            │
└─────────┬─────────┘          └───────────────────────────────┘
          ↓
┌─────────────────────────────────────────────────────────────┐
│                      基础设施层                                │
│   DeepSeek（LLM） │ BGE-small-zh（embedding） │ Qdrant（向量库）│
│                 BGE-Reranker-v2-m3（精排）                    │
└─────────────────────────────────────────────────────────────┘
```

### 1.1 后端横切线（模块 2-8 落地，不是「加了个后端」这么简单）

```
                   FastAPI 后端（src/backend/）
   ┌──────────────────────────────┐
   │  接口层：读接口 + 写接口 + 鉴权 │
   │   · 读接口：orders/logistics/ │
   │     products/online（限流 read 桶）│
   │   · 写接口：refund（限流 write 桶） │
   │   · 资金闸：review/execute    │
   │     （限流 write 桶 + JWT admin）│
   │   · 登录：auth/token（独立 auth 桶）│
   └──────────────┬───────────────┘
                  │
   ┌──────────────┴──────────────────────────────┐
   │  横切组件（每条是一个「模块」的要点）           │
   │  · MySQL：连接池 + 唯一约束幂等（模块 2）      │
   │  · Redis：Cache Aside + 空值哨兵 + 降级（模块3）│
   │  · MQ：Redis list，退款工单异步化 + 幂等消费（模块4）│
   │  · 限流：滑动窗口，read/write/auth 三桶（模块5）│
   │  · 熔断：三态 CircuitBreaker（模块5）          │
   │  · 退款状态机：pending→approved/rejected→refunded │
   │     条件 UPDATE 乐观锁（模块5）                │
   │  · 鉴权：手写 HS256 JWT + pbkdf2（模块8）      │
   │  · 出网白名单：egress 校验 BACKEND_URL（模块8） │
   │  · 容器降权：appuser + cap_drop ALL（模块8）   │
   └─────────────────────────────────────────────┘
```

- **横切线 vs 接口的关系**：接口是「业务面」（查订单、退款），横切组件是「非功能面」（数据持久、缓存、削峰、防打爆、防越权、防投毒、防提权）。后者每条都能被问成一道后端题。
- **模块 6 分布式（偏认知，无独立组件）**：CAP/BASE、一致性（强 vs 最终，本质 = 读能否读到旧值）、分布式 ID（雪花）、分布式事务（2PC/TCC/Saga）、服务发现——单机代码里没有落地点，纯认知储备。

## 2. 数据流（一句话）

> 退款写路径（refund_order）走 MQ：/refund 同步校验 + 查订单金额（金额下沉，LLM 无权填金额）→ 发消息到 Redis list → 消费者异步落库 + 通知人工（模块 4，解耦/削峰/幂等消费，Redis 挂回退同步）。审批/执行（review/execute）挂 JWT admin 鉴权——真正动钱的接口在「钱闸」，/refund 只生成待审工单、无资金流、不加鉴权。

用户问题 → AgentSession 追加历史 → 意图路由（规则命中直接执行，未命中走 ReAct）→ LLM 输出 `tool_calls`（JSON 指令）→ 代码执行对应工具（商品咨询走 RAG，订单/物流/库存走 MySQL 后端，退款走 MQ 异步落库）→ 结果回灌 → LLM 再决策 → 最终答案。

## 3. 数据层架构：元数据单一数据源（SSOT → Domain → Derived）

> 横切线之一：所有「元数据 → 派生数据」走一条单向链路，消除散落。详见 [data-sync-architecture.md](data-sync-architecture.md)。

```
源数据层 SSOT（唯一真相）: products.md + seed.py + category_synonyms.md
    ↓ parse（唯一 parser）
实体层 Domain（有 schema）: Product / Order / Logistics / Stock
    ↓ materialize（派生）
派生层 Derived（可重建）: 向量库 + BM25 + jieba词典 + 意图触发词 + 评测白名单 + MySQL + Redis缓存
```

- **单向数据流**：源 → 实体 → 派生，派生永不反向写源；消费方（tools / hybrid_retriever / eval）不自己解析源，import 派生层。
- **数据分治**：价格/品牌/类别是**静态属性** → 进知识库（products.md）；库存/订单/物流是**动态属性** → 走 MySQL 工具实时查。stock 表已去价格，价格唯一真相在 products.md。
- **知识域隔离**：商品（product）和政策（policy）分两个 kb_type 独立检索，`get_return_policy` 只在政策库检索，不混商品库。
- **同义词/特征词**是「查询侧领域知识」（人维护第二源 `category_synonyms.md`），不是商品真相，不在自动提取范围。

## 4. 评测体系架构（两层评测 + 数据飞轮）

> 横切线之二：检索层评「召回到没」，回答层评「生成对没、编造没」。详见 `tests/eval_retrieval.py` / `tests/eval_answer_quality.py`。

| 层 | 评什么 | 怎么评 | 关键设计 |
|---|---|---|---|
| **检索层** | 召回质量 | Recall@3 + MRR，四档难度标注集（字面→精确词→同义改写→场景描述） | 标注集是「第二源（人工维护）」，运行时校验 expected 是否在派生层 title 集合 |
| **回答层** | 生成质量 | accuracy（LLM-as-judge）+ faithfulness（结构化层） | **验证与生成分离**：硬编造（品牌/订单号/价格/状态）用确定性白名单抓，白名单从源自动生成；LLM 只判 accuracy |

- **faithfulness 分层下沉**：`final_faith = struct AND llm_faith`——struct 抓硬事实（订单号/价格/品牌/物流地点，白名单从 products.md + seed.py 自动生成），LLM 只判语义编造。改源数据，判定代码零改动。
- **LLM-as-judge 的坑**（已踩）：裁判无 ground truth 会误判（拿现实品牌判 demo 虚构品牌）、accuracy 和 faithfulness 不正交会确认偏误；N=3 多数票消采样噪声；`eval_judge_calibration.py` 四档样本校准裁判（3/4 通过）。
- **故障注入**：`src/backend/fault.py` + `/debug/fault`（`ENABLE_DEBUG_FAULT` 门控，默认关），评测 ReAct 边界 / 工具异常 / 写操作错误处理时注入超时/脏数据/空返回。
- **评测集集中化**：`tests/cases.py` 单一入口（检索 30 条 + 回答质量 7 条 + 压缩 3 条），改 case 只改一个文件。
- **数据飞轮**：`tests/regression.py` 坏 case 池（回流/去重/复活/毕业/lock）+ `eval_retrieval.py` 接入——评测失败自动回流成回归集，攒够按 fail_type 分组找共性根因系统性修（不逐个 patch）。
- **评测集区分度**：合成题天然虚高，真实坏 case 才打得出区分度（数据飞轮回流）。

## 5. 可观测架构（Trace + MetricsStore + 压测/fuzz）

> 横切线之三：埋点分「单次」和「聚合」两层。详见 `src/infra/observability.py`。

- **Trace（单次）**：LLM 耗时/token（含 DeepSeek 前缀缓存命中量）+ 工具耗时/step/空返回 + 结束原因（正常/异常/死循环/超步数）。
- **MetricsStore（聚合）**：进程内多次对话聚合 —— 技术成功率 / P99 / 平均延迟 / 平均 token。
- **压测**：`tests/bench_backend.py` 三档（热缓存/冷缓存/限流验证），产出 P50/P95/P99/QPS。
- **鲁棒性 fuzzing**：`tests/fuzz_backend.py`（163 断言）+ `tests/fuzz_tools.py`（210 断言），构造孤立代理/非字符串/超长等脏输入，抓到「孤立代理三连炸」真 bug。
- **分层监测**（待落地）：召回端空返回 vs LLM 端错返回，两层分开埋点，对应数据飞轮的两条补法。

## 6. 选型理由（常被问「为什么这么选」）

> 全量选型对比（每个选择的替代方案 + 为什么不用）见 [tech-selection.md](tech-selection.md)。

| 决策点 | 选择 | 为什么 |
|--------|------|--------|
| LLM | DeepSeek（deepseek-v4-pro） | 便宜 + 中文好 + OpenAI 兼容（原生支持 Function Calling） |
| Agent 编排 | **手写 ReAct 循环**，不套 LangGraph/LangChain | 理解底层「LLM 只输出指令、代码才执行」，要说明循环；框架封装了循环反而盖住要点 |
| 工具交互 | Function Calling（不手写正则 ReAct） | API 契约保证格式可靠，避免「正则解析 Thought:/Action:」的格式地狱 |
| RAG 角色 | 包装成 `search_products` 工具，和其他工具平级 | RAG 在 agent 里就是一个查询工具，路由交给 ReAct 自动选，不用写 if-else |
| Embedding | BGE-small-zh-v1.5（512 维） | 中文优化 + 本地免费（零 API 成本）+ 数据量小 512 维够用 |
| 向量库 | Qdrant 本地文件模式 | 无需 Docker（中国大陆网络限制）+ API 简洁 + 数据量小本地够用 |
| 数据库 | MySQL（连接池 + 唯一约束幂等） | 主流（索引/事务/锁要点）；SQLite 只是零配置起步，迁 MySQL 是「真实工具」演进 |
| 缓存 | Redis（Cache Aside + 空值哨兵 + 降级） | 缓存是旁路、可重建副本；减轻 MySQL 读压力，缓存挂降级查库不拖垮真源 |
| MQ | Redis list 模拟（退款工单异步化） | 削峰/解耦/可靠性，不引 RabbitMQ/Kafka（数据量小）；消息只带 order_id，金额消费者重查 DB 得出 |
| 限流 | 滑动窗口（read/write/auth 三桶） | 比固定窗口准（不突刺）；auth 独立桶防「爆破登录顺带打爆业务写接口」 |
| 熔断 | 三态 CircuitBreaker（closed/open/half-open） | 下游挂掉快速失败，不真调后端；按下游粒度分（demo 单实例） |
| 鉴权 | 手写 HS256 JWT + pbkdf2 密码哈希 | 零依赖 + 必要点（alg=none/时序攻击/过期）；密码存慢哈希防彩虹表 |
| 元数据管理 | SSOT 三层（源 → 实体 → 派生） | 单一数据源 + 派生可重建；消除「源改了派生忘同步」的散落 |
| 检索策略 | category 预过滤 → BM25+向量混合召回 → 双低拒答 → RRF 融合 → Rerank 精排 | 预过滤在召回时就锁类别，Rerank 只对已锁类别的候选精排；「召回优先 or 拒答」动机见 6.2 |
| 动态数据 | 价格/库存走工具实时查，不写进向量库 | 数据分治：向量库是「快照」，动态数据走工具才有时效性 |
| 多轮记忆 | 全量保留 + 摘要压缩（超预算压旧轮为摘要，保留关键实体） | 丢轮次会丢订单号（断跨轮指代），摘要压缩用可控 token 代价换关键信息不丢 |
| 防御 | 白名单 + 步数上限 + 截断 + 数据/指令分离 + 写权限开关 + 四层注入防御 | 五类坑的「层层兜底」，不追求「一次保证 LLM 走对」 |

### 6.1 量化数据（「有一个量化数据」硬项）

| 指标 | 数值 | 说明 |
|------|------|------|
| 混合检索 Recall@3 | 0.57 → **0.97** | 推翻 Rerank 绝对阈值（0.6 误杀口语 query）→ 改召回层双低拒答；30 条四档难度评测集 |
| Rerank 延迟 | 170ms → **16ms** | torch CPU 版 → CUDA（RTX 5070） |
| MySQL 迁移回归 | Recall@3 0.9667 不变 + refund 并发 1 工单 | SQLite→MySQL 没改坏检索；唯一约束并发兜底 |
| RRF k 值实验 | 纯 RRF：k=10 Recall 0.75 / k=100 0.69（k 越小越好）；RRF+Rerank 四档全 0.91 | 结论：**k=60 是论文默认值，真正保效果的是 rerank**（k 值被 rerank 抹平） |
| 后端压测 | 热缓存 P50 94.5ms / QPS 608；冷缓存 P50 3.7ms；限流精确 100 放行后 429 | 反直觉：**热比冷慢 25 倍**（每请求 4 次 Redis 往返，限流器先于连接池成瓶颈） |
| 鲁棒性 fuzzing | fuzz_backend 163 断言 + fuzz_tools 210 断言全绿 | 抓到「孤立代理三连炸」真 bug（quote/embedding.encode/HTTPException 回显三处 500） |
| 评测指标 | Recall@3 + MRR + accuracy + faithfulness | `tests/eval_retrieval.py` + `tests/eval_answer_quality.py`，回答质量品牌迁移后 baseline 待重跑定稿 |

### 6.2 召回策略：为什么「召回优先、拒答兜底」（场景驱动）

这是**电商客服场景**的策略，不是通用结论：

- **动机是转化率**：卖东西看转化率，宁可多召回、不轻易拒答。把「判断权 + 话术权」交给 LLM 做客服回复润色，而不是在召回层用绝对阈值误杀边界 query——踩的坑就是 Rerank 绝对阈值 0.6 误杀口语 query（Recall 0.97 掉到 0.57），改成召回层双低拒答才回到 0.97。
- **四维置信度分类 → 对应策略**：

  | 召回层状态 | 判断标准 | 策略 |
  |-----------|---------|------|
  | 双高 | 向量 + BM25 都命中同一答案 | 直接推 |
  | 单高一致 | 两路 top1 相同 | 软推 + 确认 |
  | 单高冲突 | 两路 top1 不同（如「出门乱跑」向量=漏食球错、BM25=牵引绳对） | 列候选软推（两路都列，让用户选，不偏袒精确词/语义） |
  | 双低 | 向量 top1 低分 + BM25 无召回 | 拒答 / 转人工 |

- **三层结构（判断与生成分离）**：①置信度判断层（硬编码规则）→ ②策略映射层（硬编码规则）→ ③话术生成层（LLM 按「策略标签 + 检索结果」生成话术）。前两层确定性、可测试，只有话术交给 LLM——和「验证与生成分离」同一哲学。
- **场景相关性（关键）**：这套「召回优先」是电商的答案，不是普适的。换成**医院问药品**——安全优先、错不得，策略反过来：宁可拒答转人工，也不给低置信度答案。**策略跟着业务目标走，不是跟着检索指标走。**

## 7. 当前状态与不足（「诚实讲不足」用）

**已落地的**（后端 8 模块 + agent 生产级四件套）：

- 后端：SQLite→MySQL（连接池+唯一约束幂等）→ Redis 缓存（Cache Aside+空值哨兵）→ MQ（退款异步）→ 高可用（限流/熔断/退款状态机乐观锁）→ 分布式（认知）→ 部署（Docker 三容器）→ 网络安全（JWT+最小权限+出网白名单+容器降权）。
- Prompt Injection 四层防御：prompt 级（数据/指令分离）+ 代码级（写权限开关/金额下沉/写工具单次执行）+ 架构级（沙箱/最小权限/出网限制/数据分级）。
- 评测体系：检索层 + 回答层（faithfulness 结构化下沉）+ 数据飞轮 + 故障注入 + fuzz。
- 可观测：Trace + MetricsStore + 压测 + fuzz。

**诚实的缺口**（项目当前的不足，直接说明）：

1. 🔴 **水平越权（IDOR）**：`/orders/{order_id}` 无身份校验，改订单号能查任何人的订单。demo 的 agent 没有「登录用户」概念，修它要贯穿 agent→tools→backend 三层带用户 token，和主线无关，没做。规范：`WHERE order_id=%s AND uid=%s`，不能靠前端传 uid。
2. 🟡 **token 无法主动失效**：JWT 签发后 TTL（1h）内一律有效，改密码/踢下线拉不回来；`jti` 已埋没验，只靠短 TTL 缓解。
3. 🟡 **转人工仍是 mock**：工单本地生成（`TK` 前缀），不接真实坐席系统；「在线状态」用环境变量 CS_ONLINE mock。
4. 🟡 **后端数据是种子数据**（非生产数据），真实上线量化（准确率/延迟/成本的线上数字）没做。
5. 🟡 **系统设计没做**：10 万并发怎么设计、容量估算、性能优化——这是剩下的最大一块。
6. 🟡 **分层监测待落地**：召回端空返回 vs LLM 端错返回还没分两层埋点。
7. 🟡 **品牌迁移后 baseline 待重跑**：8-28 品牌真实化后，回答质量 baseline json 还是旧品牌产物，待重跑更新。

**数据库是单机 MySQL**（无主从/分库分表），高并发架构是「系统设计」主线要补的内容，不是当前代码里有的。
