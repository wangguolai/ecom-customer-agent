# 2026-09-20 批次总结

> 起点是一个用户报的 bug：「第二轮回复里原样带着一行 `` `search_products(query="三文鱼 成猫粮")` ``」。
> 一天下来挖出 **两个线上功能一直是坏的**、**五批修复**、**一次模型分层的实测否决**，
> 以及**数据飞轮的三个盲区**。全部有实测数据支撑，没有一条是推演。

## 一、P0 · 两个线上功能一直是坏的（查延迟问题时顺出来的）

**根因同一条**：切到推理模型（`deepseek-v4-pro`）时没人注意「**思考模式默认开启、默认 effort=high**」。

| 功能 | 症状 | 实测证据 |
|---|---|---|
| **上下文压缩** | **从未生效过** → 历史无限膨胀（Token 爆炸） | `max_tokens=300` → `completion=300, reasoning=300, content=''` |
| **画像抽取** | **从未被自动写入过** | `max_tokens=400` → `completion=400, reasoning=400, content=''` |

机制：**推理 token 计入 `completion_tokens`，而 `max_tokens` 封顶的正是它** → 预算被推理整段吃光 →
`content` 一个字都没有 → 两条路径的守卫各打一行 stderr 就跳过（静默失效）。

### 修法（实测矩阵定出来的，不是读文档猜的）

| 场景 | 结果 |
|---|---|
| 摘要 · 指令在 system + 关思考 | 🔴 **不摘要，直接续写对话**（实测输出「订单…物流显示已签收。」） |
| 摘要 · **指令尾置 + 关思考** | ✅ `completion` 300→**60**，摘要完整 |
| 抽取 · 关思考 | ✅ 400→**68**，JSON 正常 |

**「机械任务关掉思考」这个直觉是错的**——不把指令从 system 挪到最后一条 user 消息，
关思考反而更糟。这条是实测才发现的，纯读文档永远看不出来。

## 二、五批修复

### 1. 规则路由词表 + 工具调用文本泄漏

**根因链**：「比较喜欢吃」（副词）被 `SUMMARIZE_WORDS` 的裸词「比较」判成「对比多款」→
路由到 summarize → 走**不带 tools** 的纯生成 → 模型想调工具却无工具 → **把调用写成了文本**。

判据是**不对称代价**：漏（走 LLM）多一次调用但答案对；错（纯生成无工具）→ 反问走偏 / 泄漏。
所以**只做减法**：删裸「比较」，只加「比较一下」；刻意不加「比较下」（会被「比较下来」命中）。

**分层处置**（安全关键）：无已执行工具 → 降级重跑 ReAct；**工具已执行 → 禁止重跑**
（`transfer_to_human` 不落库但会产出两个不同工单号 + 自相矛盾话术）。

### 2. 伪菜单走规则路由 + 会话压缩落回会话层

**菜单**：6 项里 4 项掉 LLM 决策（规则层要求「订单号+关键词」双命中，菜单项没参数）。
修法：菜单项带 `intent` id（**不是工具名**，白名单校验）→ 有参直通工具 / 无参**固定反问（零 LLM）**。

**会话压缩**：`session_store.save` 存的是**请求开始时读到的原始 history**，而压缩改的是内存副本
→ 压缩结果每轮被丢弃 → 历史单调增长 → **每轮重新压一遍**（摘要的钱花两遍、收益一遍没拿）。

### 3. 模型分层路由（含一次实测否决）

**你的判断**：「真实企业做分层路由，小模型先解决便宜问题，难问题才走深层模型」——
能挂到项目已有原则上：「判断交规则、表达交模型」往上推一层 = **决策用强模型、表达用机械用快模型**。

**实测**：话术生成 flash 1063ms vs pro 2607ms；ReAct 决策 flash 736ms vs pro 2169ms（选出的工具相同）。

**但「按步数闪切」被实测否决**：

| 配置 | 步数 | 耗时 | `search_products` 调用次数 |
|---|---|---|---|
| 全 pro | 4 | 9.87s | **2 次** |
| **flash 起步 + pro 升级** | **7** | **11.37s** | 5 次 ← **最差** |
| 全 flash | 4 | 8.2s | 4-5 次 |

**同一循环里换模型，步数反而最多。** 所以最终是**静态分层**：决策轮固定 pro，表达/机械固定 flash。
（全 flash 更快但 `search_products` 调用翻倍——那是可观测的行为退化，质量待评测。）

### 4. 类别跨轮丢失（用户实测报的）

「我想知道**猫猫**吃什么」→「有没有别的品牌的」→ **狗粮混进了猫粮推荐**（实测 3 条）。

两个独立问题：
- 词表缺**泛指词**（`猫粮` 的触发词里没有「猫」「猫猫」）
- **类别信号不跨轮**——第二句一个类别词都没有 → 不锁类别 → 全库检索

修法：「类别下沉」（**与「金额下沉」同一哲学**——能从上下文结构化拿到的参数不让 LLM 填）+
词表补泛指词。**`category` 刻意不进 `TOOL_SCHEMAS`**：LLM 看见它就会乱填。

### 5. 模型分层之外的其它观测补全

推理 token 单列（`reasoning_ratio` 口径含摘要调用）、trace 落库加列 + 幂等迁移、
`--effort` 边界校验、裁判钉死参数（否则 A/B 两臂评分标准不同）。

## 三、数据飞轮强化（回答「今天做的算不算飞轮修复」）

**结论：不算。** 今天修的 7 件事**一条都不是从池里来的**，全是用户手工发现的，
而且是**逐个 patch**——飞轮的设计哲学是「攒够 → 按 fail_type 分组 → 找共性根因系统性修」。

**但今天暴露了飞轮的三个盲区**：

| 盲区 | 被哪条 bug 印证 |
|---|---|
| **池里全是单轮场景** | 「类别跨轮丢失」——单轮 case **永远测不到** |
| **只挂检索线 + 路由线** | 「工具调用文本泄漏」是**生成路径**的 bug，两条线都不覆盖 |
| **有脚本但零断言** | `eval_context_compression.py` **只打印不 assert**——摘要失效跑过它却全绿 |

### 强化内容

1. **检索线加「类别锁定」判据**（第二组判据，不是替换）
   - `RETRIEVAL_MULTITURN_CASES`：`turns` 长度 1 = 单轮类别锁定；≥2 = 跨轮继承
   - 判据是**类别纯净度**（top-K 不得出现非期望类别），不是 titles——
     这类 bug 的症状是"混进别的品类"，用 titles 判会把"类别对了排序不同"也算失败
   - **走与生产完全相同的补参路径**（`_resolve_category` 复刻 `_with_context_category`
     + `_search_products_sync` 的优先级）——否则"评测通过"不等于"线上生效"
   - 独立飞轮池 `retrieval_multiturn`（复测要重放 turns，和单轮池不是同一套逻辑）

2. **压缩评测补断言**（把"假覆盖"堵上）
   - 断言：确实压缩了 / 产出摘要消息 / 关键实体全保留
   - **外加一条守测试数据本身的断言**：「对照组（丢轮次）必须真的丢东西」——
     否则这条 case 退化成送分题，没人会发现
   - **补断言当场抓到第二条假覆盖**：「多订单序数指代」只有 198 token，
     **从没触发过压缩**（`EVAL_MAX_TOKENS=500`）→ 一直是送分题

3. **生成线明确归属**：不硬塞进飞轮（飞轮判据是程序化的，生成线目前只有单元断言），
   由 `tests/test_reasoning_and_leak.py` 的 27 条守。

## 三·B、代码审核轮（飞轮强化那一批）——抓到 3 个严重问题，其中一个是我的真回归

| # | 问题 | 处置 |
|---|---|---|
| **S1** | **泛义词跟具体词抢分**（`detect_category` 是「命中词多者胜」） | **拆表 + 两轮打分**（具体词优先、泛义词兜底） |
| **S2** | `find_recent_category` 把**内部注入块**当用户发言 | 复用 `INTERNAL_MSG_PREFIXES` 登记表跳过 |
| **W1** | 评测里的类别决策是**生产逻辑的复制品** | 删掉，**直接调生产函数**（单一事实源） |
| **W2** | 判据把「召回空返回」和「类别污染」混判 | 拆成两条，空返回时打印 `label` |
| **W3** | 无条件信任 LLM 给的 `category` | 加白名单校验，非法值丢弃 |
| **W4** | 下沉的类别**不进 trace** | `add_tool` 加字段 + 落盘（复用已有列，无 schema 变更） |

**S1 的实测形态**（`code-reviewer` 用新旧词表对拍全仓 case 查出）：

| query | 零食表 | 狗粮/猫粮表 | 错在哪 |
|---|---|---|---|
| 「洁齿骨，能让**狗狗**当饭吃吗」 | 洁齿骨=1 | 狗+狗狗=**2** | **狗粮赢** → 预过滤把「洁齿骨」（零食）整个滤掉 |
| 「有没有**猫咪**吃的洁齿骨」 | 洁齿骨=1 | 猫=1 | **打平 → 不锁** → 退回全库检索（正是本批要修的形态） |

**而且新判据抓不到它**：MT 判据只判「返回里出现了非期望类别」，判不出「该锁没锁」
（不锁时期望类别通常仍能被检索到 → 假绿）。

**修法**：`data/category_synonyms.md` 拆成「具体词」+「泛义词（兜底用）」两段，
`detect_category` 两轮打分。修复后主指标**保持 0.7306 不倒退**、洁齿骨两 case 正确锁零食。

**教训**：**改词表这种「看起来只会变好」的改动，必须做新旧对拍**——
`detect_category` 是「命中数多者胜」的**竞争式**打分，加任何词都会影响其它词的相对权重。

## 六、本批的「元教训」（比任何单个 bug 都值钱）

1. **「设了不报错但不生效」是本项目最高频的失败形态**
   —— `temperature` 在思考模式下是空操作、`reasoning_effort` 的哨兵用字符串会被归一化抹掉、
   `max_tokens` 被推理吃光、`session_store` 存了没压缩的 history。**全是"看着在跑、其实没生效"。**

2. **备注/文档里写错的「依据」会被下一轮当成已验证结论复用**
   —— 我写过「`source_turn=None` 可佐证」，核实后那列**根本没被 INSERT 过、恒为 NULL**。
   **错误的依据比错误的结论更危险**，因为它看起来像证据。

3. **测量本身要先验证**（项目的 memory 里已有这条，今天又犯一次）
   —— 我差点把「零 LLM 路径要 2.2 秒」当成 bug 报出去，实际服务端只花 **13 毫秒**，
   2.2 秒是我每个请求新建 `httpx.Client` 的连接开销。**复用连接后是 0.02 秒。**

4. **黑名单必然漏项，白名单 + 静态断言才是「不会漏」的组合**
   —— 会话历史导出用前缀黑名单排除内部注入，实测漏掉了 `NO_TOOL_SYNTAX_HINT`；
   改成「只放行摘要 + 已登记轮次」的白名单，并加源码静态断言扫注入点。

5. **删/改要区分「过期」与「没价值」**
   —— 考点文件里 5 条「第一问级」内容，其中 2 条是**标记过期**（写着"待解决"但早已解决）、
   3 条是**空壳**。删过期是止损，删空壳是清理——判断依据不同。
