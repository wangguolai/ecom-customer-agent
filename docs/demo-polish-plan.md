## 一、库存数据（问题 1）

### 现状
`src/backend/seed.py` 的 `_SEED_PRODUCTS`：162 个商品 `qty` 全为 100。

### 设计：确定性 + 有代表性

**必须确定性**——评测要可复现，不能每次跑不同库存。

```python
# seed.py
_QTY_RANDOM = random.Random(20260918)   # 固定种子，产物可复现

# 缺货档：显式指定（测「没货了」话术 + 能否推荐替代品）
_QTY_OUT_OF_STOCK = {"P003", "P020", "P055", "P077", "P101", ...}  # ~8 个，覆盖犬粮/猫粮/零食
# 紧张档：1-5 件（测「库存紧张」话术）
# 其余：随机 20-300
```

**⚠️ 硬约束（防改坏评测）**：以下商品**必须保持有货**，因为现有评测 case 依赖——
- `优能猫粮（麦富迪牌）`（case「纠错-商品类型」查它的货）
- `洁齿骨（麦富迪牌）`（case「工具返回空结果-库存查询」查它的货）
- 订单 5 条里引用到的商品（用户查订单时会顺带问货）

**实现方式**：显式排除表 + 固定种子，而不是纯随机——随机值不可控，将来要测「缺货」得翻数据碰运气。

## 五、agent 缺陷两条

### 5.1 「只有 3 款」（问题 2）—— 真 bug

**根因**：`_search_products_sync`（`tools.py:521`）返回格式里**没有任何规模信息**，LLM 看到 3 条就推断「只有 3 款」。

**修法**（用户选「工具返回带规模信息」）：

```python
return (
    f"[检索策略：{label}]\n"
    f"{STRATEGY_HINTS[label]}\n"
    f"⚠️ 以上是本次检索返回的前 {len(results)} 条，**不代表知识库中只有这些**——"
    f"用户要更多时换关键词再检索，不要对用户说「只有 N 款」。\n\n"
    + "\n\n".join(parts)
)
```

**为什么不用「返回真实总数」**：语义检索里「总数」没有精确定义（「皇家猫粮」该算 12 款还是 54 款？取决于粒度）。**假装知道一个数字，比承认「这是前 N 条」更危险**——后者是诚实的，前者会造出新的错误陈述。

**为什么结构化的规模信息比 prompt 约束可靠**：呼应项目「判断与生成分离」——把确定性信息放代码里，别指望 LLM 自己推。

### 5.2 内部编号 `P057` 泄露（问题 3）

**根因**（诊断出来的，比表面严重）：不是 LLM 幻觉，是**工具返回里就有**——
```python
parts.append(f"[{i}] {title}（product_id: {product_id}）\n{text}")
```
而 `product_id` **必需**（`check_stock` 要它）。所以问题不是「删掉」，是**没区分「给 LLM 用」和「给用户看」**。

**修法（双层）**：
1. **数据层**（主）：工具返回里显式标注它是内部字段——
   `（product_id=P057｜内部字段，仅供你调 check_stock，**不要对用户展示**）`
2. **指令层**（兜底）：`SYSTEM_PROMPT` 补一条「不要向用户展示商品编号（P0xx 这类）」

**代价**：工具返回变长（每次多 ~15 字符 × 3 条）。可接受——准确性优先于这点 token。
