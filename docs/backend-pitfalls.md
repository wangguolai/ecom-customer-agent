# 真实工具后端 —— 深坑记录

> 从「内存 mock」升级到「FastAPI + SQLite + HTTP 工具调用」引入的坑。
> 踩坑日期 2026-08-20。状态：已踩实 / 已分析，**怎么做待讨论**。

---

## 🔴 坑 1：退款幂等性缺失（已修复，2026-08-20）

**现象**：同一订单、同一金额连发两次退款，生成两个工单。

```
第 1 次 -> 已生成退款工单 RF3A0D25F8 ...
第 2 次 -> 已生成退款工单 RF5906ABBB ...   ← 重复！
同订单同金额工单数：3
```

**原因**：`POST /refund` 没有幂等键，每次请求都 `INSERT` 一条新工单。HTTP 重试、用户双击、agent 重复调用，都会产生重复工单。

**正确做法**：写操作必须幂等。真实做法是「幂等键」——客户端传一个唯一请求 ID（如 `refund_id`），后端用它去重；或用「订单 + 状态」做业务幂等（同一订单「已退款」就不再退）。这里直接 `INSERT`，重复请求 = 重复副作用。

**已修复（三阶段）**：① SQLite 时代加「同订单 + 同金额」去重（先查后插）；② 2026-08-24 MySQL 迁移改 `UNIQUE(order_id, amount)` 唯一约束兜底——先查后插有并发竞态（双插），唯一约束让数据库硬兜底，并发双请求只产生 1 工单；③ 模块 5 高可用升级 `UNIQUE(order_id)`（一个订单一个工单，拦「同订单退 50 又退 80」，金额下沉后更明确）。生产更标准的是客户端幂等键（refund_id），demo 用业务字段简化。

## 🔴 坑 2：后端无鉴权（已踩实）

**现象**：不用任何 token/key，直接 requests 就能查订单、发退款。

```
查订单（无鉴权） -> 200 {'order_id': '20240818001', 'status': '已发货', ...}
发退款（无鉴权） -> 200 待人工审批
```

**原因**：FastAPI 接口没有任何鉴权中间件。本地 demo 无所谓，但只要后端有公网入口，任何 HTTP 客户端都能裸调。

**正确做法**：接口要加鉴权（API key / JWT / 内部服务鉴权）。尤其「写」接口（退款）更要控制。agent 调后端是「内部服务调用」，至少要 API key + IP 白名单。

---

## 🟡 坑 3：工单状态机缺失（已踩，见 Prompt Injection 那部分）

**现象**：`refunds` 表里的工单只有 `待人工审批` 一个状态，插进去就死在那，没有「审批 → 批准/拒绝 → 退款到账」的流转。

**原因**：只做了「生成工单」，没做「审批流程」。这条链是断的——防御靠的是「审批没实现」，不是「审批拦住了」。

**正确做法**：工单要有状态机（`待审批 → 已批准 → 已退款` / `已拒绝`），且状态流转要由**代码层/人工**驱动，不能由 LLM 驱动。诚实讲：demo 阶段审批流程是 mock 的，生产要接真实审批系统。

---

## 🟡 坑 4：SQLite 并发锁（已解决：迁 MySQL，2026-08-24）

**现象**：30 个线程并发发起退款，全部成功，没触发 `database is locked`。

**原因**：SQLite 是「单写者」模型，但这里的操作都是毫秒级快操作 + sqlite3 默认有 busy timeout，30 并发撞不上写锁窗口。**「没触发」≠「没问题」**——生产写密集（几百 QPS）会触发锁竞争。

**正确做法**：SQLite 适合「读多写少、低并发、单机」场景；真实高并发要换 Postgres/MySQL，或至少 SQLite 加 WAL 模式 + 连接池。这里「每请求 `sqlite3.connect` + `close`」也没有连接池，是 demo 写法。

---

## 🟢 坑 5：两套数据源不一致（已解决：stock 去价格，2026-08-24）

**现象/原因**：商品价格/信息存了两处——知识库（`products.md` → Qdrant）和后端（`stock` 表）。两处是**手动同步**的，没有关联。改一处忘改另一处，价格/库存就漂移。

**正确做法**：这是「数据分治」的代价——向量库是「快照」，动态数据走工具。但「价格」同时出现在两处（Qdrant 商品描述 + 后端库存），需要明确「谁是真源」。真实做法：动态数据（价格/库存）只在后端，Qdrant 里不放价格，或加同步机制。

---

## 🟢 坑 6：启动依赖（已分析）

**现象/原因**：agent 依赖后端先起，后端挂了订单/物流/库存查询全废。现在靠「工具里 catch 超时返回友好错误」兜底，但没有「健康检查 / 自动重启 / 降级」。

**正确做法**：真实系统的「进程编排」——后端要有健康检查，agent 侧要能感知后端状态。当前是「手动起 uvicorn + 工具超时兜底」，离生产还差健康检查 + 熔断降级。

---

## 🟢 坑 7：异常处理不完整（已分析）

**现象/原因**：工具里 catch 了 `ConnectionError` / `Timeout`，但没处理——后端返回 500（内部错误）、返回非预期 JSON、`resp.json()` 解析失败、请求体序列化失败。

**正确做法**：HTTP 调用的异常面不止「连不上」和「超时」。要处理：非 2xx 状态码、响应格式校验、JSON 解析异常。当前 `if resp.status_code != 200` 只覆盖了部分。
